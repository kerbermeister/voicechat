# Принятые архитектурные решения

Дата: 21 октября 2026.
Основание: пользователь согласовал стек, делегировал выбор групповых звонков, подтвердил Google Play Services и потребовал Docker и GitHub Actions.
Это проектные решения. Конфигурация Compose, workflow, приложение и реальный деплой пока не реализованы.

Детализация: [архитектура v1](architecture/README.md). Для управления звонками выбран собственный Go control-service; раннее «если потребуется» заменено этим решением. Продуктовые допущения, границы метаданных и блокирующие проверки перечислены отдельно.

## 1. Один VPS

Серверную часть проектируем для одного Linux VPS с публичным адресом. Разные компоненты запускаются как отдельные контейнеры на одной машине, а не на отдельных VPS:

- HTTPS reverse proxy и раздача Flutter Web;
- Synapse;
- PostgreSQL;
- хранилище зашифрованных вложений на постоянном томе;
- LiveKit SFU для групповых звонков;
- coturn для личных звонков и согласованный TURN-путь групповых звонков;
- небольшой сервис авторизации звонков, если потребуется;
- push-шлюз к FCM.

Для десятков пользователей и одной группы до 10 участников один достаточно мощный VPS — разумная стартовая архитектура. Ориентир для планирования: 4 vCPU, 8 ГБ RAM, 80–100 ГБ SSD/NVMe. Это инженерная оценка с запасом, не измеренная минимальная конфигурация и не гарантия ёмкости. Размер диска зависит от вложений и срока хранения; лимит трафика, качество канала и производительность CPU нужно проверить.

Нужны доступные TCP/UDP-порты, домен и DNS. HTTPS-прокси сам по себе не обслуживает весь WebRTC-трафик. Порты LiveKit и coturn должны быть разведены. Если потребуется TURN/TLS на TCP 443 на том же IP, спроектировать маршрутизацию TLS/SNI; не обещать, что два сервиса смогут независимо занять один порт. Проверить доступность резервного транспорта из ограниченных сетей.

Второй VPS не требуется, но нужны внешние сервисы: GitHub Actions/реестр образов, FCM, доставка почты и место резервного копирования. Резервная копия вне VPS может храниться в объектном хранилище или на другом устройстве владельца. Хранение единственной копии рядом с БД не защищает от потери VPS.

Один VPS — единая точка отказа. При обслуживании, перезапуске или сбое возможен перерыв сервиса; бесшовные обновления активных групповых звонков не обещаются.

## 2. Групповые звонки

Выбран LiveKit SFU с E2EE. Клиент публикует один исходящий аудиопоток, сервер пересылает его получателям. Приоритет — уменьшение исходящего трафика и числа соединений мобильного устройства. Фактическую задержку и устойчивость измерим; SFU не гарантирует меньшую задержку при любом расположении сервера.

Сервер не получает открытые медиаключи. Клиенты передают их только доверенным участникам через аутентифицированный зашифрованный канал. Авторизация входа на SFU не заменяет E2EE и управление ключами. Смена состава участников и отзыв устройств должны приводить к предусмотренной смене ключей. При несовместимости E2EE вызов не переключается на открытый режим.

Личные звонки остаются прямыми WebRTC с TURN-резервом. Переход из личного вызова в групповой сеанс будет спроектирован отдельно.

## 3. Восстановление истории: оба способа

Основной удобный путь — подтверждение нового устройства с доверенного телефона или браузера. Предлагаемый интерфейс: QR-код либо сравнение проверочного кода на двух устройствах с явным подтверждением. Использовать механизм проверки выбранного SDK; не сводить доверие к кнопке в неподтверждённом push-уведомлении.

Резервный путь — индивидуальный случайный ключ восстановления, созданный клиентской криптографической библиотекой. Это секрет доступа к защищённому хранилищу ключей, а не пароль аккаунта, не код из почты и не общий ключ сервера. Точный формат определяется SDK; собственный формат и собственную криптографию не изобретаем.

При первичной настройке приложение:

1. Создаёт криптографическую идентичность и настраивает зашифрованный backup ключей.
2. Предлагает сохранить ключ восстановления в менеджере паролей, скопировать для безопасного хранения или распечатать.
3. Просит проверить сохранённый ключ, чтобы случайное закрытие экрана не считалось успешным резервированием.
4. Показывает состояние резервной копии и предупреждает перед выходом из последнего доверенного устройства, если восстановление не настроено.

Копия для восстановления должна находиться у пользователя независимо от единственного телефона. Для семьи возможна бумажная копия в безопасном месте. Ключ не отправляется открытым текстом через почту, push, логи или собственный чат.

На VPS хранятся зашифрованные сообщения, файлы, резервные копии ключей и защищённое хранилище секретов, но не открытый секрет, которым администратор мог бы расшифровать историю. Действующие устройства хранят нужные криптографические материалы в локальном защищённом хранилище; особенности браузера рассматриваются отдельно.

При утрате телефона пользователь входит в аккаунт, вводит сохранённый ключ и восстанавливает доступную резервную копию ключей, затем историю и вложения. История восстанавливается в пределах сохранившихся данных и ключей: ключ восстановления не воссоздаёт удалённые файлы и не заменяет серверные резервные копии.

Если потеряны все доверенные устройства и ключ восстановления, аккаунт можно восстановить отдельно, но обещать расшифровку старой истории нельзя. При компрометации ключа потребуется отзыв устройств и сброс/смена секретов по процедуре SDK; смена ключа не отменяет уже полученный доступ к старым копиям.

## 4. Docker Compose и GitHub Actions

Цель — одна команда запуска после однократной подготовки машины, DNS и секретов. Предполагаемый интерфейс: `docker compose up -d`. Это целевой контракт; пока Compose-файл отсутствует.

Подготовка включает Docker Engine/Compose, домен, порты, параметры почты/FCM, секреты, постоянные тома и начальную конфигурацию Synapse. Шаблоны и воспроизводимые шаги подготовки войдут в репозиторий. Повторный запуск не должен пересоздавать ключи сервера или удалять данные.

Проектируем CI/CD:

1. GitHub Actions выполняет анализ и необходимые тесты.
2. Собирает Flutter Web, собственные Docker-образы и подписанный Android APK. Готовые сторонние сервисы используются из зафиксированных образов.
3. Публикует образы в GHCR с привязкой к коммиту/релизу; сохраняет APK как артефакт релиза.
4. Доставляет описание релиза на VPS по SSH и запускает проверенный deploy-скрипт. Собираем на runner GitHub, не на VPS с активными звонками.
5. Скрипт проверяет конфигурацию и место на диске, выполняет предусмотренное резервирование перед миграциями, загружает конкретные образы и обновляет Compose-сервисы.
6. После healthcheck и проверки доступности отмечает успешный релиз. Одновременные деплои сериализуются.

Для первого этапа предлагается запуск деплоя вручную из Actions или по тегу релиза; конкретный триггер утвердим при реализации workflow. Приватный/публичный статус GitHub-репозитория и адрес ещё не определены.

Данные остаются в постоянных томах. Обновление не использует удаление томов. Откат образа возможен только при совместимости схемы БД; несовместимые миграции требуют отдельного восстановления, а не автоматического обещания rollback.

Секреты не входят в Git, APK или браузерную сборку. Ключ подписи APK и доступ деплоя хранятся в защищённых секретах CI; постоянные runtime-секреты — на VPS с ограниченным доступом. Ключ подписи APK резервируется отдельно для возможности обновлять установленное приложение. Проверка SSH host key обязательна; production-секреты не выдаются workflow из недоверенных pull request.
