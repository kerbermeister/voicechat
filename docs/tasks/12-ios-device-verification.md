# Подтверждение webapp через Safari на одном iPhone

Сообщение пользователя: Safari уже авторизован, установленное на рабочий стол
webapp просит подтвердить новое устройство. После «Принять проверку» в Safari
webapp остаётся в ожидании; эмодзи не появляются.

Воспроизведена гонка SDK: encrypted ready может прийти через sync раньше
HTTP-ответа на отправку request. Раньше транзакция регистрировалась после
этого ответа, поэтому ready терялся. Теперь регистрация и начальное состояние
устанавливаются до отправки. Ошибка начальной отправки закрывает транзакцию;
запоздалые ready не могут её возобновить. Убраны также откаты состояния после
завершения отправки request/start/ready, если входящие события уже продвинули
сверку. QR-данные готовятся до ready.

Четыре теста с управляемой задержкой HTTP проверяют маршрутизацию раннего
ready, закрытие при сетевой ошибке и сохранение состояния после отправки
ready/start. Ни один из этих шагов сам по себе не выдаёт доверие устройству.
SAS/QR, проверка ключей и исходный десятиминутный срок сохранены.

На одном iPhone фоновая страница может быть приостановлена. В ожидании
добавлено объяснение переключений между Safari и webapp. Кнопка принятия
начинает протокол; завершение требует сравнения эмодзи и подтверждения
совпадения в обоих окнах.

Связь воспроизведённой гонки с конкретным сеансом пользователя не доказана:
сервер видит зашифрованные to-device события. Приёмка на физическом iPhone
остаётся обязательной; автоматический тест не заменяет эту проверку.

## Повторное зависание после c57e2fa

Пользователь подтвердил: Safari показывает «Ждём начало сверки», webapp —
«Ждём ответ» даже спустя 30–60 секунд. Первая правка не закрыла этот сценарий.

Настоящие два клиента с отдельными SQLite-хранилищами, vodozemac и локальным
Synapse получили одинаковые SAS и семь эмодзи. Проверка прошла и без остановок,
и при поочерёдном abort/resume sync. Два опубликованных web-клиента во внутреннем
браузере дошли до экрана сверки; на новом отображались семь эмодзи. Созданные только для этих проверок
локальный и production аккаунты деактивированы; доверие в web-проверке не выдавалось.

Обнаружена зависимость автоматического продолжения own-device проверки от
`addPostFrameCallback` диалога. Продолжение перенесено в `DeviceVerifications`:
проверка может начать SAS после ready без открытого диалога и кадров интерфейса.
Параллельные callback не запускают шаг дважды; отмена/закрытие прекращают
продолжение, ошибка видна и не запускает бесконечные повторы. Принятие входящего
запроса и подтверждение совпадения эмодзи остаются явными действиями.

Новый тест без widget/pump падает на опубликованном контроллере (шаг не запускается)
и проходит после переноса. Это подтверждает зависимость от отрисовки, но не доказывает
устранение конкретного сбоя iPhone. Ожидание теперь отдельно показывает, получен ли
ready: «Запрос принят. Обмениваемся данными для сверки эмодзи».

## Запуск и невидимые эмодзи после 422ea49

Пользователь сообщил: webapp показал белый экран примерно на две минуты.
После нескольких попыток эмодзи появились в webapp, а Safari показал вкладки
«Эмодзи / Код» без самих эмодзи. Три числа во вкладке «Код» отображались;
пользователь подтвердил проверку и вошёл. Поэтому последняя попытка дошла до
SAS; отсутствие картинок нельзя считать отсутствием обмена ключами.

В опубликованном клиенте используются внешние fallback-шрифты для эмодзи.
Все 64 символа SAS теперь поставляются локальными PNG Noto Emoji (около 281 KiB),
с именами Unicode, текстовыми accessibility labels и fallback-названием при
ошибке картинки. Вычисление SAS, сравнение и выдача доверия не изменены.
Тест декодирует весь алфавит и проверяет мобильную компоновку и числовой код.

Отдельно обнаружено неограниченное ожидание в стандартном bootstrap Flutter
3.47.7: перед загрузкой приложения он ждёт serviceWorker.getRegistration(),
а четырёхсекундный тайм-аут начинается только после этого вызова. Bootstrap
теперь вызывает loader без serviceWorkerSettings. Проверка с настоящим кодом
SDK loader и зависшим mock getRegistration: раньше приложение не стартовало
и тайм-аут не был установлен; теперь стартует без обращения к worker.
Cleanup worker при обновлении старой регистрации также unregister-ит себя
и вызывает navigate для контролируемых страниц. Это не доказательство цикла:
если регистрации нет, SDK не создаёт новую. Первоначальная модель трёх
перезагрузок принудительно подставляла контролируемого клиента каждый раз
и не отражала это условие; как доказательство реального цикла она отклонена.
Сохранённые ключи, IndexedDB, localStorage и существующие сеансы не очищаются.

Обычный Roboto уже включён в release assets через --no-web-resources-cdn;
первоначальная гипотеза внешнего Roboto как причины белого экрана отклонена.
Механизм блокировки запуска воспроизведён, но сетевого trace с iPhone нет:
считать именно двухминутную задержку и стабильность повторных переключений
окончательно исправленными можно только после повторной проверки устройства.
