# Выбранные технологии и обоснование

Дата: 21 октября 2026. Основной стек согласован пользователем. Конкретные версии, адаптеры и интеграции требуют прототипирования. Решения по развёртыванию и восстановлению описаны в architecture-decisions.md.

## Согласованный основной стек

| Часть | Предложение | Обоснование |
| --- | --- | --- |
| Android и веб | Flutter / Dart | Общая кодовая база интерфейса и логики, собственный дизайн, возможность добавить iOS |
| Основа переписки | Matrix, сервер Synapse | Использовать существующий протокол комнат, синхронизации и зашифрованных сообщений |
| Клиент Matrix | Matrix Dart SDK + flutter_vodozemac | Кандидат с поддержкой целевых платформ; необходим прототип криптографии и восстановления |
| Серверная БД | PostgreSQL | Хранение данных Synapse, учётных записей, событий и зашифрованной истории |
| Вложения | Media store Synapse на диске VPS | Хранить шифротекст файлов отдельно от БД; резервное копирование в другое место |
| Личные звонки | WebRTC + STUN/TURN (coturn) | Прямой путь, если доступен; TURN как резервный транспорт |
| Групповые звонки | LiveKit SFU на VPS + E2EE | Выбрано архитектором по поручению пользователя: снизить исходящий трафик телефона |
| Дополнительный backend | Небольшой Go-сервис, если необходим | Проверка доступа к звонку, выдача короткоживущих токенов; не дублировать учётные записи и сообщения Synapse |
| Android-интеграция | Kotlin / Core-Telecom, push через FCM и совместимый шлюз | Управление звонком средствами ОС; это отдельная платформенная часть Flutter-приложения |
| Развёртывание | Docker Compose, HTTPS reverse proxy | Начальный запуск на одном VPS, управляемые обновления и резервное копирование |
| Репозиторий | Один Git-репозиторий | Клиент, дополнительный сервис, инфраструктурные шаблоны и документация вместе |

Redis, отдельный поисковый сервер и Kubernetes пока не предлагаются. При выборе конкретного режима компонентов проверить их обязательные зависимости. Локальное хранилище и индекс выбрать по результатам прототипа SDK: ориентир SQLite на Android и браузерное хранилище на вебе, без обещания одинаковых адаптеров и свойств защиты.

## Почему Flutter; альтернативы

Flutter подходит для интерфейса приложения, общего на Android и вебе; iOS потребует платформенной интеграции и тестирования, а не только пересборки.

Альтернатива — React/TypeScript для веба и React Native для мобильного клиента. Хороший кандидат при приоритете веб-интерфейса или опыте команды в TypeScript. Переиспользование типов и логики не устраняет различий UI и необходимость проверить мобильную интеграцию Matrix-криптографии.

Kotlin Multiplatform также возможен, но на данном этапе не вижу преимущества, которое оправдало бы дополнительную сложность для небольшой команды и двух стартовых платформ.

## Почему готовая основа переписки

Малое число пользователей снижает требования к мощности, но не сложность E2EE, нескольких устройств, восстановления ключей и синхронизации. Предлагается собственный интерфейс поверх Matrix, а не обязательное использование готового интерфейса Element.

Synapse — готовый backend преимущественно на Python с компонентами на Rust. Выбор Synapse не означает необходимость написать собственный Python-сервис. PostgreSQL обслуживается через Synapse, приложение не изменяет его таблицы напрямую.

Альтернатива — собственный backend на Go или TypeScript/NestJS с PostgreSQL. Он потребует отдельного выбора поддерживаемого E2EE-протокола и совместимых библиотек для всех клиентов. Не считать AES/TLS или WebSocket готовым решением этой задачи.

Dart SDK Matrix имеет лицензию AGPL-3.0 согласно странице пакета. Модель распространения исходников и совместимость зависимостей нужно проверить до окончательного выбора; открытие удалённого репозитория или публикация исходников сейчас не выполняются.

## P2P и групповые звонки

При полном mesh на 10 участников получается 45 парных связей; каждый участник отправляет аудио девяти другим. Это архитектурная оценка числа связей, не результат измерения качества. Предпочтение SFU для мобильных групповых звонков — инженерная рекомендация, а не доказательство невозможности mesh.

Принятая схема:

- Личные звонки: прямой WebRTC, при необходимости TURN.
- Группы: SFU LiveKit пересылает зашифрованные медиаданные.
- E2EE звонка включено у всех участников; несовместимость не приводит к тихому отключению шифрования.

SFU не является прямым P2P. TURN тоже пересылает трафик через сервер, но не является сервером смешивания аудио. Устойчивое соединение через произвольные сети нельзя обещать исключительно через прямой путь.

Гибрид требует двух путей звонка, отдельного жизненного цикла и проверки сценария добавления третьего участника. На первом этапе предлагаем новый групповой сеанс вместо обещания бесшовного преобразования личного звонка. Более простой вариант — все звонки через SFU, но он ещё сильнее расходится с исходным пожеланием P2P.

## Сквозное шифрование и история

- Ключи содержимого доступны доверенным клиентам. Сервер хранит шифротекст сообщений, файлов и резервных копий ключей.
- На новом устройстве недостаточно одного входа по почте: доступ к истории требует доверенного устройства или секрета восстановления.
- При потере всех доверенных устройств и секрета нельзя обещать расшифровку старой истории.
- Поиск выполняется локально; сначала загружается и расшифровывается история, затем строится индекс. Не использовать серверный полнотекстовый поиск по открытому содержимому.
- Для LiveKit ключи генерировать на клиентах и распространять через аутентифицированный E2EE-канал. Сервер выдачи токенов не получает медиаключи. Политика смены ключей при входе/выходе и отзыве устройства требует отдельного проектирования.
- Для прямого WebRTC аутентифицировать согласование соединения через защищённый канал, включая привязку участников и отпечатков сертификатов.
- TLS обязателен дополнительно к E2EE. E2EE не скрывает автоматически сетевые адреса, состав комнат, времена и размеры событий.
- Стандартные реакции Matrix обычно не шифруются. Также необходимо отдельно рассмотреть typing, receipts и имена комнат. Если требование «всё шифруется» распространяется на них, стандартный Matrix без доработки не закрывает его. Согласовать границы до реализации.
- Защита локального кэша и ключей, уязвимости клиентского кода и доверие к обновлениям веб-клиента — часть модели угроз; E2EE не защищает уже захваченное устройство.

## Android и внешние зависимости

Для обычных Android-устройств предложен FCM как канал пробуждения без открытого текста переписки. История и файлы остаются на VPS. Нужен push-шлюз, совместимый с выбранным backend; FCM не заменяет синхронизацию сообщений или сигнализацию звонка.

Принудительная остановка приложения через настройки Android отличается от закрытия интерфейса: FCM требует повторного открытия приложения. Фоновые звонки обязательно проверять на реальных телефонах, с разрешениями уведомлений и ограничениями энергосбережжения. Пользователь подтвердил наличие Google Play Services у всех пользователей; устройства без них не входят в первую версию.

Для регистрации по почте нужен SMTP-сервис. Местоположение VPS выбирать после измерений доступности и задержки из сетей пользователей. Один VPS остаётся единой точкой отказа.

## Проверки выбранного стека до основной реализации

1. Flutter Android ↔ веб: Matrix E2EE для текста, изображения и аудио; восстановление ключей на новом устройстве; повторный запуск браузера.
2. Подтверждение и отзыв устройства, смена состава комнаты, отсутствие утечек содержимого и ключей в логах.
3. Локальный поиск по восстановленной истории, включая сообщения старше первоначально загруженной страницы.
4. Групповой звонок с E2EE на 10 участников, выбранные браузеры, реальные Android-устройства, восстановление сети.
5. Входящий вызов при заблокированном экране и выгруженном процессе; исключить дубли звонка при нескольких устройствах.
6. Личный прямой звонок и TURN-резерв; согласовать сценарий перехода в группу.
7. Проверить удобство, доступность и время начальной загрузки Flutter Web.
8. Зафиксировать версии и лицензии только после проверки совместимости SDK. Проверка документации не заменяет работающий прототип.
