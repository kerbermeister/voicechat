## Подтверждённая причина

`acceptDirect` проверял свободный слот до запроса push, затем ожидал освобождение
микрофона и без повторной проверки записывал `active`. Старый входящий за это
время мог закончиться, а другой звонок уже занять слот. Позднее завершение старого
accept заменяло новый active закрытой сессией. Две регрессии на54 падали:
[red-incoming-owner.json](red-incoming-owner.json).

Один owner guard исправил перезапись, но ещё5 тестов выявили незавершённый Future
принятия после local/remote/close и сообщение ошибки старой попытки поверх новой:
[red-incoming-cancellation.json](red-incoming-cancellation.json).

## Изменение

Входящий резервирует active до push/platform await и не допускает параллельного
или повторного принятия. После каждого этапа проверяются объект сессии,
поколение, завершённость и жизненный цикл контроллера. Публичный Future использует
существующий cancellation latch подготовки: local end, remote end своей сессии
и close освобождают ожидание; поздний результат продолжает только свою очистку.
Старый end не отменяет новую подготовку. `beforeMedia` ограничен45с. Ошибки push
показываются только текущей попытке; эта проверка используется и групповым accept.
Микрофон открывается существующим `DirectCall.answer` после авторизации.
Wire API, криптография, проверка устройств, параметры качества и хранилище не меняются.

42 адресных проверки PASS; полный клиент647 PASS/4 условных skip, анализ чистый,
8 проверок version/package PASS. Финальные11 регрессий после правки видимости
fixture-helper также PASS, включая настоящий45с предел (test timeout55с).
Это controller/HTTP/RTC fixtures; сквозной UI результат описан отдельно выше.
