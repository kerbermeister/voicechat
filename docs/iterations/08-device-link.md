# Вход и подключение устройства

План реализации (24 октября 2026):

1. Создавать случайное имя локального хранилища автоматически; убрать профиль и обязательную фразу из входа и регистрации.
2. Хранить браузерный AES-GCM CryptoKey в IndexedDB как non-exportable. Это удобство доверенного браузера: доступ к его профилю или коду сайта позволяет открыть историю. Не обещать парольную блокировку такого хранилища.
3. При первом входе нового аккаунта создать identity и backup; показать аварийный ключ восстановления. Не заменять существующую identity.
4. На дополнительном устройстве закрыть переписку экраном подключения. Выбрать существующее устройство, выполнить Matrix SAS: эмодзи по умолчанию, цифровой код по выбору. Отмена, несовпадение и таймаут не дают доступа к ключам.
5. После подтверждения запросить стандартные Matrix SSSS secrets только у проверенного устройства того же аккаунта; проверить и загрузить backup. Только затем сохранить локальную готовность. Ключ восстановления остаётся альтернативным входом.
6. Проверить анализатор, Flutter tests, настоящий WebCrypto и сквозной сценарий двух изолированных браузеров; подготовить свежие демо-аккаунты и группы. Проверки VPS и физических устройств указывать отдельно.

Миграция прежних локальных хранилищ не требуется. Старые данные автоматически не удаляются. Выход отзывает сессию и удаляет локальную базу; отдельной парольной блокировки автоматического профиля нет.

## Реализация и приёмка

Подключение использует существующий Matrix SAS и SSSS secret sharing без собственного криптографического протокола. Новое устройство начинает SAS; принимающее не начинает встречную сверку. При единственном другом устройстве запрос отправляется автоматически; при нескольких пользователь выбирает, где подтвердить вход. После успешной проверки и сохранения отпечатков запрашиваются self-signing/user-signing/backup secrets именно у выбранного устройства того же аккаунта. Перед открытием переписки проверяются секреты, подписывается собственное устройство и загружаются ключи старой истории. Локальная готовность привязана к account/device ID и записана в зашифрованный secret cache, не в серверные account data.

Пройденные проверки: анализатор; Flutter tests (160); WebCrypto в настоящем Chrome (включая reload, non-exportable ключ, блокировку второй вкладки, повреждения и привязку записей); регистрация с подтверждением email на локальном Synapse/Mailpit; три изолированных браузера одного аккаунта с отказом при несовпадении и успешными цифровым и emoji SAS. Создаются три пользователя, две группы и зашифрованное сообщение до входа второго устройства; тест проверяет расшифровку сообщения на новом устройстве и reload. Санитизированный результат — `prototype/verified-device-link-run.json`.

Локальные реквизиты и каталоги браузеров: `.prototype/device-link-demo.json`. VPS-реквизиты: `.prototype/vps-device-link-demo.json` (0600, не Git). Старые standalone UI-сценарии с ручным профилем/фразой не являются приёмкой нового входа. Низкоуровневые vault/lab сценарии сохраняют явные фразы.

Физические Android-устройства, Safari и полный криптографический аудит не проверялись. Автоматический браузерный ключ обеспечивает удобство доверенного компьютера; он не защищает от доступа к профилю браузера или вредоносного кода сайта. Клиентские данные прежних форматов не мигрируются.

## VPS

Историческая ручная публикация: проверенный клиент был опубликован на https://univc.duckdns.org отдельным web-only hotfix-образом `voicechat-client:device-link-20261024`. Базовый release и общий proxy override сохранены. Фактическое состояние: `/srv/voicechat/runtime/client-hotfix.json`; дополнительный Compose override: `/srv/voicechat/runtime/compose.client-hotfix.yaml`. Изменения рабочего дерева не коммитились: следующий обычный deploy использует свой manifest и заменит этот hotfix. Для отката выполнить `up -d --no-deps web` с базовыми двумя Compose-файлами без дополнительного client-hotfix override.

SHA-256 опубликованного main.dart.js совпал с production-сборкой. На публичном HTTPS отдельный тестовый аккаунт прошёл первый вход, создание ключа, подтверждение второго устройства по эмодзи, расшифровку старого E2EE-сообщения и reload. Отчёт: `prototype/verified-device-link-vps-run.json`. Три пользовательских демо-аккаунта и две группы подготовлены отдельно; их E2EE identity создастся при первом пользовательском входе, поэтому они не требуют доступа к закрытому тестовому браузеру.

## Android и локальное окружение

ARM64 debug APK собран (`apps/client/build/app/outputs/flutter-apk/app-arm64-v8a-debug.apk`). Использованы JDK 21, `LC_ALL/LC_CTYPE/LANG=en_US.UTF-8`, Rust в `.prototype/cargo` и `.prototype/rustup`, `CARGO_PROFILE_DEV_DEBUG=0` (без необязательных Rust debug symbols). Итоговый APK настроен на HTTPS/WSS VPS. Проверены CRC ZIP, наличие ARM64 vodozemac и отсутствие других ABI. Это проверка компиляции и упаковки, не реального телефона. APK и SHA-256 зафиксированы в отчёте.

Docker очищен: 109 неиспользуемых образов, 7 остановленных контейнеров VoiceChat, весь неиспользуемый build cache. Работающие контейнеры и все тома сохранены. Внутри VM свободно около 27 ГБ, но Docker.raw на Mac остаётся около 52 ГБ; TRIM вернул 0 дополнительных блоков, фактическое свободное место Mac после сборки — около 1 ГБ. Штатный [способ возврата места Docker Desktop](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/macfaqs/) проверен; загрузка helper-образа зависла и была остановлена. Docker VM не сбрасывалась, snapshots и данные других проектов не удалялись.

Объединённый релиз готовится из main через штатный `Build and deploy` в режиме `full`: новый baseline включает серверные проверки и ускоренную сборку. Результат прежнего hotfix не подтверждает приёмку объединённого релиза; её нужно повторить на manifest-образе.

Объединение завершено: `39abf2d` опубликован штатным Actions в main и на VPS. Автоматический вход, emoji SAS, отказ при несовпадении, расшифровка старого сообщения и reload повторно прошли на manifest-образе. [Приёмка объединённого релиза](integrated-release.md).
