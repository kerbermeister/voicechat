# Итерация 3: основной локальный мессенджер

Объём: функциональные сценарии Android и веба поверх уже проверенных Matrix, vault/Keystore и LiveKit. Владелец подтвердил локальный стенд; реальные SMTP и Firebase пока не подключаются. [Полный статус и оставшиеся работы](../implementation-status.md) отделены от целевой архитектуры.

## Пользовательские сценарии

- Вход существующим аккаунтом; регистрация username/пароль/подтверждённая почта, отображаемое имя; восстановление пароля по почте. Локальный Mailpit принимает письма, интерфейс ящика — `http://localhost:8025`. Само приложение не признаёт адрес подтверждённым: это проверяет Synapse. Восстановление пароля отзывает сессии и не заменяет recovery key.
- Поиск пользователей по имени или точному Matrix ID, личный чат с повторным использованием существующего DM. Именованные приватные группы, приглашения, вступление, список участников, переименование, исключение по правам Matrix, выход с подтверждением.
- Текст и Unicode-эмодзи; ответы, редактирование своего текста, удаление своих сообщений/модератором. Реакция переключается повторным нажатием. Изменения отображаются через Matrix relations; удалённые сообщения исключаются из результатов поиска.
- Изображения до 10 МБ; запись голосового до 3 минут и воспроизведение. И файл, и дескриптор проходят шифрование SDK. PCM-запись собирается в памяти в WAV; Android читает выбранное изображение напрямую из URI провайдера, веб — из File/ArrayBuffer. Открытые временные копии файлов приложение не создаёт. Кэш Matrix защищён тем же хранилищем, что и ключи.
- Набор текста с ограничением частоты, статусы отправки/прочтения, непрочитанные чаты. Receipt на более новом событии подтверждает и предыдущие загруженные сообщения. Активный поиск или просмотр старой истории не отправляет новое подтверждение прочтения.
- Локальный поиск по текущему тексту с учётом правок. Догрузка истории по 100 событий; пока можно догружать ещё, интерфейс явно сообщает о неполноте результатов. Сервер не получает поисковый запрос по содержимому.
- Зашифрованная устойчивая очередь исходящих текстов, вложений, ответов, правок и реакций. Один transaction ID сохраняется между повторами и перезапусками, SDK/сервер дедуплицируют доставку. Повторная проверка сессии, состава комнаты и доверия перед отправкой; отсутствие связи не превращается в plaintext. Очередь ограничена 100 элементами, повтор идёт по sync/таймеру; застрявшую отправку можно отменить. При выходе очередь должна быть отправлена или явно отменена.
- Входящий личный звонок и групповой вызов в открытом клиенте: принять/отклонить/завершить, микрофон, участники, статус соединения. Личные — SDK Matrix VoIP/WebRTC DTLS-SRTP с TURN, группы — LiveKit E2EE до 10 подключений. SDP/ICE личного вызова идут в зашифрованной комнате. Микрофон входящего вызова не открывается до принятия.
- Три палитры, общий адаптивный интерфейс для веба/Android, проверка устройств доступна и на узком экране.

## Особенности реализации

`ChatActions` сохраняет очередь в локальной таблице Matrix account data, используя только `database.storeAccountData`. `setAccountData` и загрузка этой очереди на сервер не вызываются. Все значения этой таблицы входят в vault/SQLCipher. Подтверждение постановки в очередь выдаётся только после успешной записи; сбой записи не очищает поле ввода.

`VoiceCall` объединяет два реально используемых транспорта: `DirectCall` и `CallProbe` (LiveKit). Входящие групповые приглашения — зашифрованные сообщения Matrix с новым случайным session ID. Это локальный механизм foreground-вызова, который не заменяет запланированный control-service. Ограничение приглашения по времени, один текущий вызов на клиент, проверка прав каждые три секунды. При невозможности подтвердить права звонок прекращается. LiveKit SDK восстанавливает кратковременные медиасоединения; сквозная работа при смене сети ещё требует отдельной приёмки.

В loopback-стенде ICE принудительно использует TURN для воспроизводимой проверки резервного пути через `adb reverse tcp:3478 tcp:3478`. Внешний деплой должен использовать прямой ICE как основной путь и TURN с публичным адресом и TLS. Текущий Coturn доступен только на loopback; его разрешение loopback peers недопустимо переносить в публичный продакшен без пересмотра конфигурации.

Запись использует `record`, воспроизведение — `audioplayers`, WebRTC — уже используемый `flutter_webrtc`. Выбор изображений использует платформенные средства: HTML file input и Android ContentResolver. От файлового плагина отказались из-за открытых копий в Android-кэше. iOS не выпускается; его адаптер выбора/защиты медиа нужно реализовать и проверить отдельно.

## Проверки

```sh
python3 prototype/setup.py
docker compose -f prototype/compose.yaml up -d
# При обновлении конфигурации уже запущенного стенда:
docker compose -f prototype/compose.yaml restart synapse
python3 prototype/check_registration.py
python3 -m unittest discover -s prototype -p 'test_*.py'
cd apps/client
flutter analyze
flutter test
```

Полный запуск Android + две вкладки Chrome описан в [прототипе](../../prototype/README.md). Он дополнительно проверяет офлайн-транспорт и повторное открытие очереди, edits/replies/reactions/redaction, ciphertext серверных файлов и расшифровку на Android, typing/receipts, восстановление вложений новым устройством, запись/воспроизведение, личный TURN/DTLS и групповые медиапотоки после принятия входящих приглашений.

Ограничения реального выпуска и матрица приёмки перечислены в общем статусе; сборка APK сама по себе не означает прохождение этих сценариев.

- Личный звонок проверял входящие аудиопакеты на обеих сторонах, `dtlsState=connected` и nominated successful candidate pair с relay-кандидатом; одного состояния connected недостаточно. Перед принятием отдельно проверено отсутствие локального микрофонного stream.
- Проверены 287 зашифрованных значений в трёх веб-профилях. [Этапы прогона без секретов](../../prototype/verified-core-run.json).
- `flutter analyze` без замечаний, 16 Flutter-тестов и 4 Python-теста прошли. Реальные регистрация и восстановление пароля проверены через Synapse/Mailpit.

Эмулятор и синтетический микрофон не подтверждают качество акустики, работу закрытого Android или приёмку десяти физических участников. Полный производственный MVP остаётся зависимым от работ в общем статусе.

- Обычный UI-сценарий прошёл: вход, поиск, создание группы, текст/изображение/запись/воспроизведение, правка/реакция, настройки участников, экран 390 px, блокировка/открытие профиля и выход. Команда: сначала `python3 prototype/check_registration.py` (свежий одноразовый аккаунт), затем `node prototype/check_ui.cjs` при доступном Playwright. Снимки: [десктоп](../design/screenshots/core-web-desktop.png), [узкая веб-версия](../design/screenshots/core-web-mobile.png).
- Блокировка отменяет сетевые запросы и не ждёт зависшую попытку отправки; уже записанный элемент остаётся в очереди с тем же transaction ID. Это покрыто отдельным тестом. Старые async-обработчики закрытой очереди не переписывают её состояние.
- Для каждого личного звонка TURN-доступ запрашивается заново: истекающий пароль не кэшируется бессрочно. Видеоприглашение отклоняется до создания media; разрешение камеры эта голосовая версия не запрашивает.

Отдельная проверка `node prototype/check_signup_ui.cjs` проходит весь экран регистрации, подтверждает письмо в Mailpit и проверяет завершение SDK UIA, вход и выход. Новые личные чаты дополнительно проверяются через серверное состояние `m.room.history_visibility=joined`.
