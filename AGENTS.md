# Правила разработки VoiceChat

Применяются ко всему репозиторию. Цель — минимальное полное решение с понятным человеку кодом. Экономим код, а не корректность и проверку результата.

## Перед изменением

- Прочитать задачу, затрагиваемый код и существующие решения. Найти все вызовы изменяемой функции через `rg`.
- Определить полный охват: реализация, вызывающий код, тесты, fixtures, конфигурация, экспорты и документация.
- Проверить риски для существующих пользователей: потеря/раскрытие данных, несовместимость интерфейсов и миграций. Не расширять задачу дополнительными функциями.

## Выбор решения — в этом порядке

1. Проверить, нужна ли новая функция вообще. Для широкого запроса реализовать минимальный вариант, полностью выполняющий основную задачу.
2. Переиспользовать существующее решение проекта и его соглашения.
3. Использовать стандартную библиотеку или платформенную возможность.
4. Использовать уже подключённую зависимость. Не добавлять пакет ради нескольких строк.
5. Написать простую понятную строку, если этого достаточно; иначе минимальный читаемый код.

## Качество кода

- KISS: простая структура, ясный поток управления, содержательные имена функций, переменных и типов.
- DRY: переиспользовать реально общую логику; не создавать абстракцию для гипотетического будущего повторения.
- SOLID применять там, где это упрощает ответственность компонентов и их проверку. Не создавать интерфейсы и слои ради принципа.
- Не добавлять ненужные обёртки, преобразования типов, параметры, настройки и заготовки «на будущее». Использовать данные в естественной форме платформы.
- Сохранять обработку ошибок и валидацию при переносе или объединении кода. Исправлять корневую причину в общей точке.
- Из равных по сложности решений выбирать корректное на граничных случаях. Удаление лишнего лучше новой абстракции.
- Комментарии объясняют причину, которую не выражает код. Известное временное ограничение обозначать: `shortcut: <ограничение>, <когда заменить>`.
- Документировать запуск, контракты, ограничения и нетривиальные решения. Не пересказывать каждую строку кода комментариями.

## Сборка и развёртывание

Перед сборкой определить затронутые части по diff относительно текущего production release, а не только последнего коммита. Собирать только необходимые артефакты; не пересобирать backend или Android ради проверки исключительно веб-изменений. Изменения общего Flutter-кода могут затрагивать обе клиентские платформы — не считать их автоматически web-specific.

### Обязательный выпуск macOS-клиента

- Если изменения требуют обновления установленного macOS-клиента, задача включает сборку, подпись Sparkle и публикацию готового обновления на VPS. Выпуск входит в исходный объём работы и не требует отдельного напоминания пользователя. Один merge, локальная `.app` или обновление сайта не означают завершение такой задачи.
- Определять необходимость выпуска по diff относительно последнего опубликованного macOS-релиза, включая общий Flutter-код, нативный код, зависимости и конфигурацию клиента. Чисто веб- или серверные изменения, не затрагивающие macOS-клиент, сами по себе не требуют macOS-сборки.
- Увеличивать номер сборки, обновлять историю изменений и использовать существующий личный режим `--personal` без Apple Developer Program, постоянный ключ Sparkle и настроенный HTTPS-канал. Не создавать новый ключ при каждом выпуске, не отключать проверки подписей. Порядок выпуска: [infra/MACOS.md](infra/MACOS.md).
- Публиковать точный проверенный пакет штатным `publish_macos.py`; после публикации проверять доступность feed и архива по HTTPS, подписи/контрольные суммы и предложение новой версии через «О приложении → Проверить обновления» в предыдущей установленной версии.
- Проверять установку через кнопку с сохранением аккаунта, идентификатора устройства и доступа к прежней истории. До замены сохранять резервную копию приложения и профиля; не удалять данные или ключи Keychain для исправления обновления.
- Если выпуск или проверка заблокированы доступом к ключу, системным подтверждением либо недоступностью Mac, явно сообщить, что именно не выполнено и какое действие необходимо. Не объявлять клиентское обновление готовым, пока пользователь не может получить его через приложение.

### Выбор production-режима

GitHub Actions → **Build and deploy** (`.github/workflows/deploy.yml`) → **Run workflow**. Выбрать согласованную ветку/revision и явно указать режим:

| Изменения / цель | Режим | Что происходит |
| --- | --- | --- |
| Только клиент/web, backend и его конфигурация совпадают с production | `mode=web`, `deploy=true` | Собирается только web-образ; используется текущий immutable digest control; обновляется только web с `--no-deps`. |
| Backend, Compose, серверные политики, схемы БД, защищённые build/config-файлы; смешанный релиз или отсутствующая baseline | `mode=full`, `deploy=true` | Собираются control и web; выполняются согласованный backup, обновление служб и проверки здоровья. |
| Только сборка и публикация артефактов без изменения VPS | Нужный режим, `deploy=false` | Образы/артефакт публикуются без деплоя. В режиме `web` всё равно нужен read-only SSH к production для проверки baseline и reuse control digest. |

- Для исключительно веб-правки использовать `web`, если guard подтверждает допустимость; не выбирать `full` просто по привычке.
- Источник истины о допустимых путях — `infra/release_source.py`. Сейчас исключены `apps/client/**`, `docs/**`, корневой `README.md`, `infra/Caddyfile` и `infra/web.Dockerfile`. Остальные пути защищены, включая `AGENTS.md`, workflow и vendor: после их изменения нужен полный релиз для новой baseline. Не ослаблять fingerprint ради прохождения быстрого режима.
- При отказе web-only выяснить расхождение. Не менять вручную `backend.sha256`, `current.json`, `previous.json` или digest, чтобы обойти guard.
- Оба режима сохраняют существующие серверные/клиентские тесты и анализ. Ускоряем сборку артефактов, не отключаем необходимые проверки.
- Production `full` означает сервер + web на VPS, а не сборку всех клиентских платформ. Android APK — отдельный артефакт. Текущий **Prototype checks** автоматически собирает Android на push/PR; селективность этого workflow пока не реализована. Не обещать, что выбор `web` отключает этот отдельный CI-job.

### Локальная сборка web

Использовать Flutter и crypto toolchain из `infra/crypto-tools.json`; для Rust нужен именно указанный датированный nightly с `rust-src` и target `wasm32-unknown-unknown`. `PUBLIC_URL` должен быть задан каноническим HTTPS origin production; для локального стенда использовать отдельную конфигурацию из `infra/README.md`.

Из корня репозитория, после установки toolchain:

```sh
python3 infra/client_config.py "$PUBLIC_URL" /tmp/voicechat-client.json
cd apps/client
flutter pub get --enforce-lockfile
cd ../..
python3 prototype/build_web_assets.py
cd apps/client
flutter build web --release --no-web-resources-cdn --target lib/main.dart --dart-define-from-file /tmp/voicechat-client.json
```

Это обычный клиент `lib/main.dart`, не лабораторный `lab_main.dart`. Команды не обновляют VPS; для production использовать release workflow. Локальный генератор ассетов намеренно пересобирает их; в Actions он запускается только при промахе exact-key кеша.

### Backend и кеши

- Изолированная локальная сборка control-образа поддерживается: из корня `docker build -f infra/control.Dockerfile -t voicechat-control:local .`. Это только сборка образа, не полноценный backend-релиз: серверные компоненты также включают Synapse-модули, политики и Compose-конфигурацию.
- Отдельного production-режима `backend` сейчас нет. При изменении только backend текущий поддержанный путь — `full`. Не заменять его ручным `docker compose up control`: это обходит согласованный release/backup/rollback и может не обновить другие серверные компоненты.
- Если потребуется реализовать backend-only, переиспользовать текущий web digest и сначала обеспечить проверки совместимости клиента/API/схем, блокировку, backup, healthcheck и откат, а затем проверить настоящий переход между частичными и полными релизами. Не выдавать такую возможность за уже реализованную.
- Переиспользовать кеши инструментов и crypto assets. Их ключи включают закреплённые ОС/архитектуру/toolchain, lock-файлы, исходники SDK и скрипты генерации; изменение входов требует пересборки. Не использовать устаревшие ассеты просто потому, что каталог существует.
- Не кешировать runtime, секреты, SSH/GHCR credentials, пользовательские профили или весь `.prototype`. Cold miss должен сохранять полноценный рабочий путь сборки.
- После релиза проверять commit/digests, здоровье служб и rollback pointer. Для `web` подтвердить неизменность backend ID/StartedAt/RestartCount. Сохранять `Cache-Control: no-cache` для актуальности клиента без очистки пользовательского хранилища; демонстрация экрана остаётся default off.
- Подробные команды и ограничения: [infra/README.md](infra/README.md), [план VPS](infra/VPS.md), [проверенные замеры](docs/iterations/deployment-speed.md). Не удалять старые release-каталоги, которые ещё используются bind mounts работающих контейнеров.

## Единый реестр пользовательской приёмки

- Единственный текущий реестр непроверенного с точки зрения пользователя
  функционала — [docs/user-acceptance.md](docs/user-acceptance.md), для всего проекта,
  всех платформ и итераций. Отдельные журналы остаются техническими свидетельствами,
  а не параллельными списками того, что должен проверять пользователь.
- Агент самостоятельно выполняет все доступные проверки, включая пользовательские
  UI-сценарии в разрешённой среде. Не перекладывать на пользователя автоматизацию,
  сборку/выпуск, подготовку fixtures и то, что агент способен проверить сам.
  Успешный автотест не подменяет недоступное физическое устройство.
- После изменений, выпуска, нового замечания или ответа пользователя актуализировать
  существующую запись: стабильный ID, функция/шаги/ожидаемый результат, готовность,
  версия, устройство/ОС/браузер, дата, подтверждение или дефект и ссылка на задачу.
  Не выдумывать неуказанное покрытие и не закрывать пункт по предположению.
- Перед добавлением искать совпадающую функцию/сценарий в реестре. Повторы из
  разных итераций, платформ и формулировок объединять, дополняя условия и результат;
  сохранять сопоставление старых номеров, не перенумеровывать устойчивые ID.
- Разделять доступное к проверке, условное (нужны устройство/почта/тестовый профиль),
  найденные дефекты/ещё не реализованные задачи и подтверждённое. Не просить приёмку
  недоступной функции. Повторно принятый блок проверять только в затронутой изменением
  части, с явной причиной; новые пожелания не отменяют прежний успех целиком.
- В конце итерации давать ссылку на этот реестр и актуальный остаток, не создавать
  новый дублирующий чек-лист в другом файле. Секреты и приватный контент в реестр
  не помещать; опасные сценарии готовить на одноразовых профилях без очистки
  основного пользовательского хранилища или Keychain.

## Завершённость

- Новая нетривиальная логика, особенно безопасность, парсинг и ветвления, получает небольшой содержательный тест или проверку с assertions. Исправление включает все затронутые вызовы, fixtures и конфигурацию.
- Нельзя сокращать валидацию на границах доверия, защиту от потери данных, безопасность, доступность интерфейса, необходимые проверки реального оборудования и явно запрошенные функции.
- Не выдавать сборку, mock или эмулятор за проверку реального устройства; не выдавать включённую настройку E2EE за доказанную расшифровку медиапотока.
- В конце ответа одной-двумя строками указать, что пропущено/не проверено и какой существенный риск остался.

Пользователь назвал этот режим `/ponytail`; он действует до команды `stop ponytail` или `normal mode`. Уровни `lite/full/ultra` задаются пользователем; без отдельного выбора не придумывать дополнительные требования уровня.
